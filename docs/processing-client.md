# Swift processing client

`ProcessingClient` is an explicit asynchronous client for the local processing API. It creates or accepts a guest credential, creates sessions, uploads JSON artifacts through persisted server offsets, submits compilation with a caller-retained idempotency key, reads job status and deletes sessions. It does not discover or upload capture files automatically.

Repeating `upload` with the same bytes reuses the server's hash-bound declaration and starts from its reported offset. Responses must match the local byte hash/size, advance to the expected chunk boundary and confirm full finalization. Network failures are surfaced; retry uses the same data and credential rather than starting another job. Compilation keys are explicit UUIDs so callers can persist/reuse them. Job status must match the requested ID. HTTP errors retain their status code for later recovery UX.

The client accepts HTTPS origins, or explicit loopback HTTP origins for development, and rejects embedded credentials, URL queries and fragments. Requests use an ephemeral URLSession with cookies disabled and redirects rejected. Artifact and response budgets are 100 MB; responses currently buffer in memory before the size check, so streaming/bounded response consumption remains work before production. There is no automatic reconnection loop, background URLSession integration, Keychain credential storage or native job screen yet. Call `close()` when the client is no longer used.

`processing-probe` is a separate command-line executable that accepts only `127.0.0.1` and always uses synthetic geometry. It exercises the actual Swift client against a temporary real loopback server: guest creation, session creation, uploads, submission, client recreation with the same credential, repeated upload/submission identity, worker completion, result download/local replay and deletion followed by HTTP 404. It requires the trusted local compiler worker alongside the server. It does not prove physically interrupted transfer recovery.

The probe passed with a hash-bound report at ignored `outputs/swift-processing-probe/report.json`; its server was shut down afterward. No tokens appear in the report or command output, and no participant data was uploaded. The unsigned iPhone SDK build checks that the client is available to the native target; this is not a native UI integration or physical networking test.

## Guest credential persistence

`ProcessingCredentialStore` now provides Keychain save/load/remove operations. Items use a fixed app service and an account derived from the normalized endpoint origin. Host case, an empty root path and an explicit default port normalize to the same endpoint; different schemes/ports/hosts remain isolated. Both client construction and Keychain access reject non-HTTPS remote URLs, embedded credentials, paths, queries and fragments. Guest payloads require a UUID owner and a bounded URL-safe token; malformed/header-control characters are rejected.

The Keychain accessibility is `WhenUnlockedThisDeviceOnly` with synchronization disabled. A locked-device read error is surfaced rather than treated as “no guest,” preventing silent replacement of an inaccessible identity. This choice does not support locked-device background transfers. Removing the local item does not revoke its server credential or delete its server sessions; those need a separate explicit lifecycle. No credential is written to UserDefaults, logs or probe reports.

All 120 core tests pass, including endpoint normalization and invalid-credential rejection. A simulator-only UI probe saves a synthetic Keychain entry, terminates/relaunches the app, restores it using an equivalent origin, checks different-port isolation, deletes it and checks absence. The UI test and unsigned iPhone SDK build pass. The synthetic HTTP probe also still passes after endpoint normalization. The fake Keychain probe is excluded from physical builds and uses no real guest secret. Physical lock/unlock behavior, production entitlement configuration, Keychain-to-native-job-screen wiring and credential loss/recovery UX remain unfinished.

## Verified result download

`compiledResult` requires a succeeded job with a valid output hash before downloading its result. `ProcessingCompilationResult.verify` then checks the exact response byte hash, original uploaded input/haircut byte hashes, schema/kind and the unverified-style flag. It decodes the original canonical inputs, replays guide validation and recompiles the mesh locally with the fixed worker settings (three sides, radius scale 1). Both complete validation and mesh artifacts must hash identically to the server result. A plausible revision label or updated transport hash alone is insufficient.

All 121 core tests pass. A test alters a returned vertex while recomputing the transport hash and confirms rejection, and separately rejects a claimed personal-style verification flag. The synthetic Swift HTTP probe now runs through one actual queued compiler invocation, downloads its output and successfully replays it locally, then deletes the session. The worker and server were stopped after testing. The unsigned iPhone SDK build passes.

This strict replay is an experimental correctness gate, not an efficient production asset verifier: it recompiles on the device and exact floating-point output may differ across platforms/compiler versions, in which case it rejects rather than silently accepts. Device cost and cross-platform tolerance policy remain to be measured. The verified mesh has not yet been connected to a native job/result screen or the saved viewer history. It does not validate aesthetic suitability or repair the incomplete head reconstruction.

## Research generation client

The explicit `submitResearchGeneration` API submits a bounded description and seed with a persisted caller-supplied request key. `generatedGuides` requires succeeded status, verifies exact result-byte hash, matches the expected request, and checks the pinned research schema, unresolved units, ordered unique guide identities, finite bounded points, counts and nonzero extent. It rejects personal-acceptance claims. These checks establish transport and structure; the client does not rerun the neural model or establish style quality. The extracted source bytes can subsequently enter ModelGuideImport with an explicit hash-bound personal mapping; that step has not been connected to this request UI.

All 122 core tests pass, including wrong-request, personal-claim, duplicate-guide and degenerate-curve rejection, and the iPhone SDK build passes. `processing-probe URL REPORT --research` ran through a real loopback API and explicitly enabled Metal worker: one model invocation, 763 downloaded guides, client recreation/idempotent submission and session deletion. Evidence remains in `outputs/swift-research-generation/report.json`. Subsequent header decoding was tightened to reject Boolean/integer coercion and the core suite/build were rerun. No native generation screen or participant upload was involved; the temporary service/worker were stopped.
